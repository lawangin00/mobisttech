Run `composer install --no-dev --prefer-dist --optimize-autoloader`, `npm ci` and production builds against the pinned candidate under an authorized staging deployment; never copy live `.env` into repository history or execute migrations in a source project.
- Start only approved services after config validation, test HTTPS host separation, redirects, account/session boundaries, API/Next proxy cookies, uploads, queue and scheduler. Monitor logs without exposing tokens, customer data or backups. Keep external integrations, customer notifications and real provider payments OFF until their own approved acceptance gates pass.

## Backup architecture and recovery contract

- The existing Laravel `BackupArchive` / `BackupRecovery` is an **application-level encrypted logical snapshot and verify-only recovery** with schema/key/code identity checks; it is not a replacement for host-wide DB/private-file recovery. Preserve its distinct approval and reset gates.
- The independent `deploy/linux/backup/backup.sh` is the host-level encrypted restic snapshot: consistent `mysqldump` (single transaction + routines/triggers/events) plus local private objects, or an explicit read-only S3 private-object copy, stored into a **different off-host S3-compatible restic repository**. The backup identity has minimal source READ and backup WRITE privileges. Restic password, separate MySQL client config, and S3 credential profiles are outside Git, locked to backup account. Use bucket versioning/object-lock policy and independently retained encryption/recovery keys only after security review.
- Private S3 mode must set `APP_PRIVATE_S3_URI` to the **exact private application prefix**, with `APP_S3_SOURCE_PROFILE` restricted to source READ. Restic uses the separate `AWS_PROFILE=backup`; do not point restic at the application bucket/prefix. Never publish private objects, credentials, backup metadata or restored records to the Website.
- Consistency caveat: a MySQL transaction snapshot does **not** atomically freeze filesystem/S3 object writes. `MOBIST_WRITES_QUIESCED=yes` must be asserted by an **actual short-lived authorized application-wide write barrier** that covers queue workers and private-object writes, not a permanently hard-coded value. The example keeps backup disabled and barrier false. Therefore the timer is a **disabled readiness artifact**, not a claim that unattended production-consistent backups already operate. Design, implement and approve the automated barrier/release mechanism, failure alarm and capacity budget before activation; resume writes even on backup failure. Do not enable the live timer before then.
- Stage plaintext SQL only on an access-restricted, sized, ephemeral/tmpfs `BACKUP_TMP_ROOT`; a crash/power failure may leave an orphaned plaintext file, so enforce boot cleanup, encrypted swap policy, restrictive umask and log-free dumps. The script removes successful and failed run staging via a bounded trap; an unmounted/off-host S3 repo or unreadable key fails closed. Verify snapshot ID, restic repository metadata and SQL readback hash. Restore all private objects into an **isolated** path to verify object hashes and DB-reference integrity on a recurring recovery drill; do not assume SQL-only verification proves object recovery.
- Monitor each timer/service exit, off-site snapshot timestamp, retention, MySQL object totals, repository access, disk capacity, certificate expiry and an independently tested recovery-key escrow. Define owner-approved RPO/RTO and retention/legal hold **before production activation**. Never run automated `restic forget --prune` against live history until legal-retention and independent recovery drills are approved.

## Restore and release rollback (explicit HOLD)

1. Obtain separate owner approval for target environment, exact snapshot ID, data scope, maintenance window and rollback plan. An incident alone does not grant permission for production data overwrite or deletion.
2. Provision a **new isolated target**; verify snapshot ID, off-host key custody, source/target environment, schema/migration SHA, file-manifest hashes, MySQL engine, application release and object permissions. Never import into legacy POS/Website databases or the active production DB as a rehearsal.
3. `restic restore <approved-id> --target <isolated-private-path>` using a read-only repository identity; confirm full object readback/hash, then import the SQL into an expressly named isolated **empty** target DB. Reconcile row counts, monetary totals, owner/outlet relationships, S3 path references, preserved history, application keys and recovery-manifest schema/code contracts. No credentials or cached sessions are resurrected blindly.
4. For an approved release rollback, stop/wait for writes and queue workers, maintain a verified pre-change snapshot, activate the prior immutable release with schema compatibility **proven**; do not blindly reverse potentially destructive migrations or switch an old app onto a new incompatible DB. Validate login, Website mode, customer orders, POS stock, private downloads, queue and payment idempotency before releasing traffic.
5. Record actor/approver, target identity, timestamps, exact version and snapshot, checksums, tests and final verdict. If any key, file, manifest or accounting reconciliation fails, **stop** and preserve the failed attempt for review rather than partial cutover.
