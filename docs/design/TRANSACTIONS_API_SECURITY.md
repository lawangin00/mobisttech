# MT-1.2 - Transaction, REST and security contracts

Status: Design only. Laravel/Next.js routes, databases, providers and services have not been implemented or activated. `openapi.json` is the versioned public contract baseline; source route disposition and family mapping remain traceable through `SCHEMA_MAPPING.json` and MT-1.1.

## Transaction invariants

| ID | Required invariant |
|---|---|
| T-01 | MySQL is the only business authority. Every POS, CMS, API, CLI and worker mutation uses the same Laravel application services and policies. |
| T-02 | All inventory mutations lock the affected canonical product rows in ascending ID order, then unit/allocation rows consistently; no cached quantity authorizes a sale. |
| T-03 | Quantity stock availability is `products.qty - current holding allocations`; unit stock availability is eligible in-stock units minus holding unit allocations. In-stock IMEI slot completeness and variant selection remain required. |
| T-04 | A sale, invoice, order consumption, movement and payment linkage are committed atomically. Idempotent retry cannot create another sale, invoice, decrement or verified payment. |
| T-05 | Release/expiry and confirmation are mutually exclusive for one reservation attempt. Physical return is a new compensating operation, never a late release of consumed stock. |
| T-06 | Authoritative payable amount/currency/merchant/order reference comes from locked server records and verified provider evidence. Browser redirects and status fields never mark money collected. |
| T-07 | Historical snapshots, events, receipts and source provenance are retained. A refund-status label or physical-receipt flag alone cannot move cash or stock. |
| T-08 | Business writes and publication-version/event insertion occur in the same transaction. External effects happen after commit and tolerate retry. |

Use explicit InnoDB transactions with `SELECT ... FOR UPDATE` on indexed rows, not a read followed by an unprotected write. A locking query does not automatically lock rows in a nested subquery; lock each required aggregate explicitly. Use a consistent global order: idempotency record; existing order/invoice/return aggregate; payment rows; products ascending; stock units/IMEI claims ascending; allocation rows; document sequence; audit/event insertion. Newly created aggregate rows are private to that transaction. Never acquire an earlier lock class after a later one. For workflows without an order/invoice, begin at their first applicable class. Use bounded deadlock retry (up to three full transaction attempts); a retry reruns validation and contains no external effect. MySQL locking behavior is documented in its [locking reads reference](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html).

No database lock is held while contacting a provider, sending mail, uploading to S3 or running a backup tool. Do not use Redis locks as the stock/payment correctness boundary. `SKIP LOCKED` is permitted for claimable worker-event queues, not for silently skipping requested customer stock. Application exception paths roll back all business changes; audit of rejected requests is secret-safe and separate from a falsely committed business outcome.

### Checkout, reservations and stock

1. Authenticate the customer or establish an opaque guest-session/cart owner; reject Website admins using customer flows. Validate at most 50 lines, 1-20 units each, one outlet per physical order, current category/publication/variant and exact expected price/version. A cart is not a reservation.

   Cart add/update retains the source maximum of 99; checkout explicitly enforces the stricter 20-unit reservation-contract limit and asks the user to adjust before attempting a transaction. Preserve optional customer email. Normalize supported Pakistani mobile formats to canonical `03...` before applying the retained phone contract.
2. Claim the idempotency key; lock/create the order and lock all products in sorted order. For quantity products sum current holding allocations under the product lock; for unit products lock eligible units and active IMEI ownership. Reserve only source-valid in-stock units with complete slots and requested variant. `qty` on unit products is a derived count checked against units, not a second independent stock decision.
3. Create immutable order/item snapshots, an attempt and allocation rows. Online reservation state is `active` with a server TTL of 1,200 seconds by default, bounded 300-3,600 seconds as in the source. The deadline comparison is `now >= expires_at`; app/worker use the same UTC policy. Expired allocation cleanup acquires the same order/product locks; it cannot release a confirmed allocation.
4. Create the pending payment attempt and a durable outbound intent, commit, then contact the configured provider. A provider timeout leaves an unknown/pending attempt for reconciliation; it does not cause a second payment attempt automatically. Return a safe order/payment status or configured hosted redirect.
5. POS sales, adjustments, deletes/archive operations, imports and return-to-stock all honor the same holds. A product with open allocations cannot be changed into an incompatible variant/stock mode or physically removed. Unit allocation has a unique active-unit key. Quantity checks and changes serialize on the canonical product row.

Reservation transitions are defined in `DESIGN_ACCEPTANCE_CASES.json`. `active -> consumed` requires unexpired holdings and verified payment; `active -> released/expired` clears only that attempt. A released/expired attempt cannot be resurrected by replay. A new explicit checkout attempt may reserve again after fresh price/stock checks, without reusing a previous successful payment or creating a duplicate order sale.

COD is a deliberate safety adaptation. The source can collect cash after its short reservation expires and then report a stock exception. The target creates a `held_cod` allocation at accepted COD checkout, with no online-payment TTL expiry. It stays unavailable to other sales until collection/consumption or an explicit authorized cancellation/return process. Dispatch does not make unpaid stock available. Staff confirm cash collection exactly once; only then may the order complete and consume its held inventory. An operational stale-COD report requires human review/cancellation; it never silently releases dispatched goods. This preserves COD functionality while preventing expiry-driven oversell; MT-2.7 must test the change explicitly.

### Payment receipts and confirmation

Provider callbacks/webhooks are untrusted input until their configured provider adapter verifies authenticity and transaction status using an authentic contract. Verify expected provider, merchant/account, environment, transaction ID, order/payment association, amount, currency and final state. Store a sanitized receipt hash/event identity and timestamps, not raw secrets/card payloads. Unique event/transaction constraints supplement application checks. Provider redirects may display status only; staff cannot POST `paid=true` to bypass this service.

The OpenAPI JSON callback is a design placeholder, not a claim about a provider's wire protocol. Each authentic adapter must declare its actual content type and signature input before activation, including form-encoded callbacks where required. Verify the original signed bytes/fields before any normalization; never re-encode a payload and assume its signature still applies. Extend and validate the contract with authentic fixtures under H-02.

Under the order/payment/product locks, apply a verified receipt once. If holdings remain valid, create/link the single invoice and sale lines, update unit/IMEI and quantity states, write stock movements, consume allocations, update order/payment history and commit audit/events. Digital quotes use the approved quote amount/token/version and payment linkage without stock. Existing POS sale logic, invoice snapshots, warranty clauses and business identifiers must be called rather than reimplemented as a second Website sale path.

If payment is received after release/expiry, after cancellation, or without valid holdings, preserve the verified collected payment but enter `stock_exception`/reconciliation-required; do not automatically sell unallocated stock, erase the receipt or call the order safely fulfilled. Reconcile with explicit new-allocation authorization or a verified refund/manual compensation. Replayed matching receipt returns the original outcome; a different transaction for an already-paid attempt conflicts and is investigated, never counted as another sale. A callback claiming failure cannot overwrite an already-verified paid result. Multiple paid attempts on one order remain a reconciliation incident, not a second stock consumption.

COD collection uses its own authorized actor and immutable cash receipt, checks currency/amount and `held_cod` allocation, and follows the same consumption transaction. COD refusal/cancellation does not fabricate a refund when no money was collected. Configured disabled JazzCash/Easypaisa/Card paths fail safely with `provider_unavailable`; authentic sandbox and live activation remain H-02. No raw PAN/CVV collection, proxying or logging is designed.

### Returns, refunds and fulfillment

Preserve Website source fulfillment statuses (`pending`, `confirmed`, `processing`, `ready`, `dispatched`, `completed`, `cancelled`, `returned`) and refund statuses (`none`, `pending`, `partial`, `refunded`) as separate dimensions. Preserve historical labels even where evidence is incomplete, adding a reconciliation state rather than asserting they prove cash/stock movement. Digital orders do not enter ready/dispatched/physical-return states.

New physical return records reference original sale lines, quantities/unit identities, actor and reason. Lock invoice/return/payment/product records; reject quantities beyond remaining sold units, duplicate receipt events or an IMEI already active elsewhere. Inspection chooses sellable, damaged or quarantined stock; only explicit sellable receipt restores availability. Refund is separate, bounded by verified collected amount less already-refunded amount and connected to a provider or authorized cash-refund receipt. Keep original sale/cost/discount/warranty snapshots; append compensating movement and monetary records. Do not silently reopen expired warranty or recalculate the original invoice.

Source Website admin return/refund flags and POS `InventoryController` return-to-stock behavior are reused as validation/history inputs; neither substitutes for a complete sale-return/financial-refund service. MT-2.5/2.7 implement and verify that missing integration. Automatic provider refund is unavailable until the authentic adapter supports it; track manual verified refund evidence and outstanding obligations without claiming payment completion. No live refund is authorized by this design.

Reserve refundable balance under the payment lock before recording an outbound refund intent. Available balance subtracts both completed refunds and pending/unknown refund intents. A timeout retains that reservation until provider reconciliation proves success or definitive failure; failure releases it once. This prevents two different refund requests from each spending the same balance while external calls run outside the transaction.

### Idempotency and optimistic concurrency

For unsafe business operations require an `Idempotency-Key` of 16-128 visible ASCII characters, unique within server-derived actor/guest scope and operation. Canonical hashing normalizes decimal strings and object key order, includes operation/resource IDs and retains list order; security-relevant fields and version are part of the hash. Authenticate/authorize before replay so cached data cannot bypass revoked access. Same key and same hash returns the original safe status/resource; same key and different hash is HTTP 409. An in-flight duplicate returns 409 `operation_in_progress` with bounded retry guidance, never parallel effects.

Write the idempotency record and deterministic business outcome in the same transaction; a rolled-back failure is retryable. External intents have their own durable operation ID and provider idempotency reference. Keep response bodies for seven days as a target policy; keep durable operation/resource uniqueness and a minimal tombstone through the business record's retention period so pruning does not permit duplicate payment/sale. Encrypt or omit sensitive replay data. Existing idempotency/outbox history is imported as legacy evidence; old endpoints/keys are not blindly executable under the new protocol.

For cart, CMS, order-management and credential edits require `If-Match`/expected revision. Check the locked current version; respond 412 on mismatch or 428 when required precondition is missing. Successful state-changing response returns the new version. A new idempotency key does not waive the revision or unique-business constraint.

## REST boundary and authentication

`openapi.json` defines `/api/v1` public/content/customer/cart/order/quote contracts with explicit request/response shapes and policy metadata. JSON IDs are strings; money is a two-decimal string; timestamps are RFC3339 UTC. API versioning is path-based. Additive optional fields are allowed within v1 only if consumers tolerate them; changed meanings/required inputs/removal need a new major contract and recorded compatibility period. Keep legacy public slugs, redirects and document/order aliases; internal old POS integration endpoints retire only after their mapped replacement gates pass. `SCHEMA_MAPPING.json` records a disposition for all 316 source routes, not 316 promises to preserve old framework internals.

The customer browser and its Laravel API use one configured origin: in production Nginx sends Website pages to Next.js and `/api/v1`, `/sanctum/csrf-cookie` and customer authentication to Laravel. Backend administration uses a separate configured host. Local development uses an explicit allowlisted same-origin development proxy with new ports chosen in MT-1.3; no original ports/services are reused. The proxy forwards only to the fixed target Laravel upstream and cannot accept arbitrary destination URLs. It performs no business validation, database access or provider calls.

Use Laravel session authentication and Sanctum's first-party cookie/CSRF pattern; no JWT/localStorage bearer tokens for the browser. Sanctum documents session-based first-party authentication and the XSRF cookie/header handshake. [Laravel Sanctum](https://laravel.com/framework/docs/13.x/sanctum) The session cookie is Secure in deployed HTTPS, HttpOnly, SameSite=Lax and host-only; CSRF cookie is intentionally readable by the browser. Distinct server-side session namespaces/cookie names and guards separate customer, POS/admin and Website CMS realms. A Website admin user is not a customer user, even if both use the `users` table. No `Domain=.example` shared-admin cookie and no wildcard credentialed CORS.

The browser initializes CSRF, submits credentials to the appropriate realm and rotates session ID on login/privilege change. Logout is POST and invalidates the session/token; password changes revoke other sessions according to the preserved account-session contract. Preserve source password reset brokers, throttle behavior and non-enumerating responses; scope reset token identity by guard so equal email addresses cannot reset another realm. Roles/grants and outlet membership are rechecked on each write; a stale menu/session cache cannot retain revoked access. Source null POS permissions receive only source operational defaults, not configuration/publish rights; Website legacy null admin_role maps to source owner only for proven existing admin rows and is explicitly audited.

Next.js SSR may forward the current customer session cookie only to the allowlisted Laravel origin for private reads; it must not use an administrator/service credential to impersonate customers. Private responses, sessions, cart/order/account/payment/quote capabilities use `Cache-Control: private, no-store`, no static generation or shared cache, and never enter HTML for another request. Public navigation/catalogue metadata uses allowlisted DTOs. Frontend environment variables never contain DB credentials, provider secrets or encryption keys.

Guest-to-account cart recovery requires possession of the current server-issued guest session and a successful customer login. Lock both carts in stable ID order, merge matching product/variant lines once within the quantity limit, and surface excess quantities or unavailable items for adjustment. Reprice from canonical products at checkout, invalidate the old guest ownership, and retain an idempotent merge reference. Contact-data matching alone cannot recover another guest's cart or orders.

### Authorization matrix

| Actor | Allowed scope | Always denied / additional checks |
|---|---|---|
| Guest | Published catalogue/content/services; own guest cart/checkout; scoped order capability reads | No customer/account history, admin actions, other guest cart/order, private stock/cost/CNIC data. |
| Customer | Own account/orders/cart; eligible reviews; approved quote payment with valid capability | Website `is_admin` must be false. No cross-customer access or ability to mark paid. |
| POS admin | Exact existing operational/configuration grants plus assigned outlets | Require `shops.enter` and action permission for outlet work. Report/backup/publish grants are separate. Never gain Website admin role implicitly. |
| POS super-admin | Source global POS administration and business profile scope | Does not implicitly become Website owner; destructive restore/cutover still has separate operational authorization. |
| Website owner | Existing owner role including user/credential management and publication | Customer portal denied. Credential secrets are write-only/masked; no POS outlet privileges implied. |
| Website manager | Existing role permissions including content/orders/services/configuration/publication | No `admin-users` or `website.payment-credentials.manage`. |
| Website content_editor | Source content/services/settings and content/SEO/media/publish grants | No orders, payment credentials or operational user management. |
| Website operations | Source orders/service-requests/project-quotes | No CMS/credential/role publication powers. |
| Worker/provider adapter | Narrow allowlisted service operation tied to persisted intent or verified receipt | No arbitrary command/URL; no user-supplied system actor; no browser token accepted as provider authentication. |

The full source permission keys remain in the pinned model inventory and machine design mapping. Policies apply to object ownership and each sensitive field, not only endpoints. Return a non-enumerating 404 for inaccessible order/quote/document IDs; 403 for a known authenticated actor denied an administrative capability. Input DTOs reject fields such as roles, cost, stock, `paid_at`, `payment_status`, actor/outlet ownership and arbitrary metadata unless a specific authorized operation declares them. Server-selected actor/outlet/price cannot be mass assigned from the client. [OWASP REST authorization guidance](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html)

Guest order/quote/request access preserves capability-based behavior with scoped, revocable, expiring target capabilities. Persist only a capability hash; scope to resource and operation, default 24-hour read access, with explicit renewal through verified customer/operator recovery. Never use a bare order number, phone number or email as authorization. Quote tokens are single-resource access, not authority to change an approved amount. Redact tokens from logs/referrers and use Referrer-Policy: no-referrer on capability pages. Do not automatically accept old source APP_KEY signatures on the new host.

### API errors, pagination and limits

Error envelope: `error.code`, safe `message`, optional field errors and `request_id`; never stack traces, SQL, secrets or private object existence. Status contract: 400 malformed JSON; 401 no valid session; 403 denied capability; 404 unavailable/inaccessible resource; 409 stock/price/idempotency/state conflict; 412 stale revision; 419 expired CSRF; 422 valid JSON with invalid fields; 428 missing precondition; 429 rate limited with Retry-After; 503 disabled provider/backend dependency. Payment uncertainty returns a persisted pending/reconciliation result, not a fictitious success.

Page-based list queries preserve source pagination behavior: `page >= 1`, `per_page` default 25, maximum 100, stable sort with ID tie-breaker. Allowlist sort/filter keys; bind SQL values. Responses use `data` and `meta` containing page/per-page/total/request ID as relevant. One-resource responses use `data`. CSV/document output is a distinct authenticated media type and escapes formula-leading CSV cells; it is never returned through a public catalogue DTO.

Catalogue page size specifically follows the published source setting (12/24/36/48, fallback 24); retain newest/oldest, price and name sorting, brand/subcategory/condition/PTA/availability/price/RAM/storage filters, and comparison of up to four comparable products in requested order. Do not silently substitute the generic page-size default. Payment-option endpoints derive gateway eligibility from the owned cart or approved quote; optional wallet account input is adapter-specific and never admits card PAN/CVV.

The presentation endpoint emits only published public business identity, approved logo URL, source-registry-validated CSS variables, sanitized header/footer and catalogue display policy. It does not expose a generic settings dump. Resolve public product slugs through the dedicated by-slug endpoint; public DTOs retain approved descriptions/images/specifications while excluding IMEIs and private costs. Zero-stock listing visibility follows the published source setting; displayed availability always follows canonical stock.

The legacy project-reference/mobile lookup is retained as an access-recovery journey, but those two guessable fields no longer reveal a reusable payment token. `POST /quote-access/requests` returns a generic result; delivery of an access capability requires a verified quote contact/account or authorized operator. This is an explicit security adaptation to the source `ProjectPaymentController::find`, not a silent loss of the lookup feature. No message is sent in this design checkpoint; future delivery uses disabled/fake integrations until separately configured.

Target initial limits: login/reset 5 per minute per realm and normalized-account/IP bucket; guest/customer mutation 30 per minute per actor/IP; public reads 120 per minute per IP; provider callback 30 per minute per provider/source with replay-safe processing and provider-specific tuning before activation. Preserve stricter source per-route limits when present. Bound JSON body to 256 KiB excluding dedicated media upload; uploads have explicit source-approved type/size limits and private staging, not generic JSON endpoint bypass. Size limits/rate metrics must be tuned with fresh target tests, not interpreted as a provider SLA.

## Cache, queue and integration recovery

Use Redis initially only for derived public content/catalogue cache and non-authoritative throttling. Use database-backed sessions and durable database queue/event records initially to keep credential/session and business recovery tied to MySQL. Redis queue/session migration is optional only after measured need and recovery tests; Redis is not needed for stock locks. S3-compatible storage is for controlled media/backups, with isolated local disks during development. Document operational cost/credentials at MT-1.3; do not enable services merely because the stack lists them.

POS writes and CMS publication increment an affected `publication_versions` row and insert an invalidation event in the same MySQL transaction. A public read obtains the current version from the master and addresses a versioned derived cache key; an event failure therefore cannot make an old version authoritative. A reader concurrent with a commit may complete its pre-commit snapshot, but any read started after commit sees the new version. Never shared-cache stock-sensitive price/availability responses across versions; Next.js initially uses no-store for these reads. Redis outage falls back to bounded master reads for public content, with limits; checkout always reads master state. Cache failures never revert business commits.

Workers claim events with a lease and unique operation ID; exponential retry is bounded, terminal failures are visible to operators, and expired leases can be reclaimed. Consumers deduplicate by event ID/aggregate version and tolerate out-of-order obsolete invalidations. Invalidation failures are recoverable from the durable outbox; do not rely solely on an in-process `afterCommit` callback. Mail/provider/storage intents retry independently; unknown provider result is reconciled before issuing a new charge. Scheduler downtime cannot authorize expired reservations: writes validate deadlines inline and the scheduled cleanup uses the same service. No user-facing health endpoint exposes credentials, internal paths or provider payloads.

## Security review and required verification

Treat browser input, provider payloads, source imports, uploaded files and worker messages as separate trust boundaries. Require TLS in deployment, strict host/proxy allowlists, CSRF for all session writes, object/field authorization, safe uploads/SVG/content sanitization, audit redaction, backup key separation and explicit operational HOLDs. Preserve source media/reference and configuration recovery checks. Do not expose a general admin SQL/command/URL execution surface.

`DESIGN_ACCEPTANCE_CASES.json` records positive/negative/race/recovery cases and owners. MT-1.2 validates specification completeness, example schemas and transition invariants only. Actual MySQL races, Laravel guard/session/CSRF behavior, provider authenticity, runtime build and Playwright tests remain required implementation gates. No source test pass substitutes for them.
