# MT-2.1 - Shared backend schema and infrastructure

This checkpoint adapts the inspected Laravel schema into the shared target. It does not migrate accounts, private rows, uploads, stock, payments or application routes. MT-2.2 is the next implementation point. The implementation ledger owns current progress; MT-1.2 design artifacts remain historical design evidence.

## Traceability and reuse

The pinned POS and Website exports were inspected by applying their existing 79 migrations to empty in-memory SQLite databases, with synthetic test configuration and external HTTP disabled. No original repository code was executed in place. No source database or environment file was read. The inspector records the final surviving columns, indexes and foreign keys; a Blueprint interceptor additionally captures declared lengths, JSON types, decimal precision and enum choices that SQLite alone does not retain. Seeded source defaults are not exported or imported.

`source_pos.json` and `source_website.json` contain schema metadata only: 33 POS and 25 Website tables, totaling 735 final columns. `COLUMN_DESTINATIONS.json` assigns every column a destination, disposition and transformation rule. `TARGET_SCHEMA.json` describes the target schema generated by the reviewed compiler. `verify_shared_schema.py` checks all 79 migration hashes against MT-1.2, complete table/column coverage, planned new tables, FK destinations, and rejection of unknown/missing source columns across 116 synthetic invalid row shapes. The shape guard is not a data importer: value validation, timezone conversion, identity resolution, authorization and reconciliation are mandatory at the later import gates.

The two conventional Laravel migrations are the runtime authority. They add 62 tables (including two fresh runtime token tables) to the seven framework tables already present, yielding 69 tables, 894 columns, 117 foreign keys and 317 indexes including primary keys. Tables and constraints are separate migrations so circular historical relations can be created without disabling foreign-key checks. Rollback drops constraints before tables and preserves the existing runtime schema. Do not regenerate an already published migration to change a database; later points must add new migrations.

The existing schema is adapted rather than rebuilt from guessed models. Existing credential columns, permissions, settings, audit metadata, snapshots, JSON fields, financial columns and historical timestamps are retained. No source `app/Jobs` directory existed; framework queue persistence and processing are reused, while source console/service business jobs remain owned by their later feature points.

## Deliberate schema transformations

- POS `users` become `outlets`; Website `users`, POS `admins` and `super_admins` remain separate credential realms. `shop_id` becomes `outlet_id`, and the outlet/admin pair is unique. Retired outlet password/token columns are explicitly inactive history. New public resource UUIDs do not replace preserved business codes or prove authorization.
- Website `products` become `product_listings`, with one required canonical product FK. Cached price, quantity, availability and sync time use `legacy_*` names and cannot be mistaken for current inventory. Website product references in order items/reviews become listing references; order items also have canonical product/outlet fields. The identity map supports a source product mapping to both canonical product and listing after verification.
- Reservation attempts reference shared orders and outlets. A generated nullable unique key permits only one current active/COD hold per order. Active unit allocation uniqueness is likewise generated from release state; a free-form legacy key cannot bypass it. Source attempt history remains available.
- Active IMEI claims are unique across outlets, while `product_imeis` retains past occurrences after sale/re-entry. Composite FKs reject product/outlet, invoice/outlet, unit/product and allocation/line/product mismatches. Cumulative quantity, state transitions and concurrent stock consumption still require the later transactional services.
- All financial/audit/content relations use RESTRICT rather than source cascade deletion. Archive fields support actor/catalogue retirement. Existing financial, customer, warranty and business snapshots remain intact. Return/refund/receipt tables establish structure, not implemented refund or payment behavior.
- Money uses `DECIMAL(19,2)`; media aspect ratios retain six decimal places. Persisted dates use UTC `DATETIME(6)`, and business-date fields remain dates. Case-sensitive collations preserve external identifiers, slugs, codes, keys and digests. Internal IDs/FKs use matching unsigned BIGINT types. Currency checks restrict the initial transaction currency to PKR.
- Provider transaction/event scopes and operation identities are unique. Import lineage includes source repository/table/key and target table, run hashes, quarantine and reconciliation. A merged outcome requires a review reference; an importer must additionally verify that review and account for every row.
- Source sessions/cache/jobs/reset/access tokens are not imported. POS account-session rows remain security history, not active sessions. Legacy integration request/outbox tables are archive-only. Legacy quote bearer-token evidence is nullable/inactive; new scoped capabilities store hashes only.

Full value validation is essential: MySQL may round excess decimal scale even in strict mode, so a future importer/API must reject it before insertion. Invalid dates, overlength strings, enum mismatches, unknown columns, unresolved FKs and source currency/arithmetic discrepancies must fail or be quarantined explicitly. No private-data import acceptance is claimed here.

## Infrastructure behavior

MySQL remains the only business master. The Windows runtime and exact target accounts/ports from `../foundation/WINDOWS_SETUP.md` are reused. Both target local and disposable test schemas receive the migrations. No source services, global database service or source credentials are used.

Database sessions and the durable database queue remain the initial default. Queue dispatch waits for the surrounding transaction to commit; rollback discards that dispatch. Tests run actual MySQL-backed workers, prove retry then terminal failed-job recording, and preserve failure evidence. An after-commit enqueue callback alone does not guarantee delivery after a process crash: business services must insert their durable `domain_events`/intent rows in the same transaction and later relay/reconcile them. This point establishes and tests that storage boundary; business event consumers and provider side effects remain later feature work. Do not use a synchronous fallback for a failed financial job.

`VersionedCache` is an internal primitive for sanitized public projections only. It reads the current domain version from MySQL before looking up a versioned cache key; a committed version change bypasses an old entry. Missing versions bypass cache. Read/write cache errors do not undo business commits, and a cache read failure invokes the master callback once. A master-query failure propagates rather than serving stale state. Endpoint throttling, publication event integration and checkout use remain later API gates.

`DERIVED_CACHE_STORE=file` is the simple local default. `redis` is optional for derived public cache; connection/read timeouts are bounded. Redis is not installed or activated merely to tick a stack requirement, and is not used for stock locks, authoritative state, sessions or queues. The Redis outage test uses a reserved, non-listening loopback socket and the real Predis adapter; it does not connect to source Redis or claim live Redis success. Future shared-environment activation requires its own isolated service/recovery gate.

`PrivateObjects` writes generated, namespaced object keys through private local/S3 storage, checks payload size and SHA-256, rejects traversal/URLs/executable suffixes, rejects existing keys and symbolic links, and verifies read-back integrity. Callers must allocate unique object IDs and apply object authorization and approved content validation; this internal primitive is not a public upload endpoint or a concurrent overwrite transaction. Archive contents are never extracted here. Publication and private acquisition/backup paths stay separate; no private storage URL route is enabled.

S3 defaults to a private `mobisttech/private` prefix; deployment must use a unique environment bucket/prefix and least-privilege credentials. Real local/testing S3 access is rejected by the private-object service. Tests exercise the actual Flysystem/AWS adapter with an AWS SDK MockHandler, verifying bucket/prefix/private ACL and failure propagation without any HTTP request. They are adapter contract tests, not acceptance of a live S3 provider, IAM policy, encryption, object versioning or backup recovery. Those remain MT-3.3/MT-7.4 and applicable HOLDs. The Website receives only REST configuration and no MySQL, Redis or object-store credentials.

The implementation follows the installed framework and its primary references: [Laravel filesystem](https://laravel.com/framework/docs/filesystem), [Laravel 13 queue implementation](https://github.com/laravel/framework/blob/13.x/src/Illuminate/Queue/DatabaseQueue.php), and [MySQL exact fixed-point types](https://dev.mysql.com/doc/refman/8.4/en/fixed-point-types.html).

## Reproduction and acceptance boundary

From the repository root, start only the owned target runtime with `pwsh -NoProfile -File tools/dev/Database.ps1 Start`. Apply target migrations with `php backend/artisan migrate --no-interaction` and `php backend/artisan migrate --env=testing --no-interaction`. Never use these commands inside either protected source repository.

Run `python tools/migration/verify_shared_schema.py`, using the bundled Python runtime when needed. From `backend`, run `php artisan test --no-ansi` and `php vendor/bin/pint --test`. For the current full target schema, `php ../tools/migration/verify_mysql_schema.php api` inspects only the exact `mobisttech_test` schema and fails on unexpected tables/business rows, non-InnoDB tables or non-strict/non-UTC settings; historical checkpoint modes such as `shared` remain point-specific evidence and are not the current full-schema gate. The verifier emits only metadata and a normalized schema hash.

The controlled rollback gate uses only the disposable test schema: roll back the two MT-2.1 migrations, verify `runtime` mode gives exactly seven framework tables, reapply, and compare the `shared` schema hashes. This is not permission to roll back a populated local/production database. Actual data-import/restore/cutover stays under its separate roadmap authorization.

`MT_2_1_VERIFICATION.json` records final tests, rollback hashes, artifact hashes and limitations. No source test totals are reported as target acceptance. The roadmap, Word mirror, approved Goal/Preferences, Source of Truth and registry remain unchanged. No MT-2.2 authentication, customer ownership or authorization migration is included.
