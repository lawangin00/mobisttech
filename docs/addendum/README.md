# MT-2.8 - Addendum foundations and capability contracts

Contract version: 1.0 | Approved scope: addendum v1.1 | Baseline: `41ecc38ec3404c70fa373bdaaedc6cef0f107654`

This checkpoint implements only the additive prerequisites for sales and later approved expansion. It preserves the 73 existing tables, original schema/source mappings and all published migrations. Seven companion tables bring the schema to 80 tables. The implementation ledger owns current progress. The structural roadmap and its DOCX are unchanged.

`ENTITY_API_PERMISSION_MATRIX.json` maps all 41 approved leaf clauses to entities, permissions, reserved API contracts, owning points and acceptance requirements. Every listed business HTTP surface remains **planned, not routed**. `CONTRACTS.json` records versioned payloads, lock/identity rules and deferred consumers. `MT_2_8_VERIFICATION.json` records fresh verification and artifact hashes.

## Additive schema

| Table | Ownership and invariants |
|---|---|
| `website_operating_profiles` | Singleton `id=1`, positive version, one of three modes, FK to a published `website.mode` configuration revision. Empty means unpublished with both capabilities off. The reader rejects revision/version/mode disagreement. |
| `inventory_custody_holds` | Positive quantity against source and distinct destination products; an optional serialized unit must belong to the source product and has quantity one. Generated unique active-unit key prevents two active custody holds. Source product/released index supports current availability. |
| `stock_unit_lineage` | Each origin and successor has at most one edge; successor ID must be newer, preventing cycles. Both units remain FK-protected. Operation UUID and transfer/customer-return reason preserve provenance. |
| `acquisition_source_references` | One typed PO-receipt or trade-in reference per acquisition, with a stable UUID and indexed source-line UUID. Acquisitions keep their original party/cost snapshots. |
| `monetary_adjustments` | Exactly one invoice/order FK, positive exact decimal(19,2), PKR, stable UUID, kind, immutable approved snapshot/digest and globally one-use external effect UUID where required. Trade-in is tender; manual/promotion/loyalty-redemption adjustments are discounts in v1. |
| `project_milestone_identities` | Stable UUID, quote FK, unique positive sequence, positive exact approved amount and immutable scope snapshot/digest. Existing payment state is not duplicated here. |
| `order_item_milestones` | One-to-one companion relationship from an existing order item to a milestone; a milestone cannot be linked into a second order item. Payment attempts and receipts remain under the existing order/payment authority. |

All new FKs restrict deletion. No existing business column is removed, retyped or backfilled, and no new business row or active mode is seeded. New migration rollback checks **all** extension tables for rows before dropping any table; it refuses populated rollback. This is deployment safety, not a business reset. MySQL DDL is not transactionally atomic: apply maintenance/exclusive migration access, inspect the migration failure and restore/reconcile if DDL is interrupted; never rerun blindly over partial DDL or live writes.

## Stock custody and immutable history

An outlet's product row and its unit occurrence retain their original ownership and identifiers. A later transfer must map to an appropriate destination-outlet product, never change the original product's outlet or the original unit's product. No arbitrary product matching or silent variant conversion is approved. Transfer dispatch owns a durable custody hold against the source product; on-hand custody remains at the origin until accepted receipt, while sellable availability excludes the hold. In-transit reporting distinguishes that custody from physically available source stock. Serialized units stay `in_stock` under the hold, so their active IMEI claim cannot be stolen during transit.

MT-2.11 must authorize both outlets and validate product/variant/identifier compatibility. In one transaction, acquire source/destination product locks in ascending ID order, verify the current holds/claims, retire the origin occurrence, record the outbound quantity, allocate a fresh destination occurrence and code, move the active claim to it, add the lineage edge, record inbound quantity and close only the accepted hold. Quantity stock uses matched movements and the same hold quantities without fake serialized units. Reject/cancel releases the unreceived hold; partial receipt releases only accepted quantities. These workflows and their independent concurrent tests remain MT-2.11, not completed by these primitives.

`StockLedger::holds` combines reservation allocations with custody holds. A sale's own reservation exclusion never excludes custody holds. Duplicate cross-domain holds on the same physical unit fail snapshot reconciliation; they are not silently counted twice. Existing product, IMEI, adjustment, acquisition and stock import protections reuse this combined view. Writers must hold the source product lock before creating/changing custody holds; separate table uniqueness alone cannot serialize reservation-versus-custody races. The new table has no public writer in this checkpoint.

For an authorized customer return, MT-2.5 must create a new occurrence linked to the sold source unit, preserving its invoice/sale/IMEI history, and validate that the sold quantity has not already returned. Re-entry uses the current global IMEI constraint, so another active device blocks intake. Quantity returns use line-level returned-quantity accounting, not unit lineage. The append-only lineage table is a relationship safeguard, not permission to return or transfer a unit.

`acquisition_source_references.source_line_id` is a reserved UUID in the typed owning domain, not a trusted caller-supplied foreign key. MT-2.9 creates persisted PO/receipt ownership; MT-2.13 creates trade-in valuation ownership. Those writers must resolve the source-line UUID and validate product/outlet/received quantity before attaching this reference in the acquisition transaction. Partial receipts may share one PO line but must have distinct acquisition/reference IDs. Additional relational links become additive migrations at the owning points. No synthetic placeholder supplier/PO is required for existing acquisitions.

## Money and milestone contracts

`MoneySnapshot` rejects floats, exponential values, leading-zero variants, sub-cent values, zero/negative amounts and decimal overflow. All monetary amounts are canonical two-place strings; financial currency v1 is PKR. An adjustment has a stable UUID, immutable source identity, reason and fixed treatment. A trade-in credit offsets tender due and never masquerades as a price discount. Loyalty earning points remain a separate non-money ledger; a confirmed redemption may produce one authoritative discount snapshot. Percentage engines, stacking, rounding, reversal and eligibility rules remain their feature points.

`FinancialReferences` requires an owning transaction and locks its parent. It appends/replays a reference; changed parent, amount, fields or digest is rejected. It does not change invoice totals, collect payment, grant customer ownership or reapply an effect on retry. The sales/order owner must authorize a fresh actor, validate the approved source and currency, enforce discount/tender limits, lock the aggregate, persist exact totals/snapshots and consume stock in the same transaction. Reversals reference the original adjustment and create a new approved compensating record; they never mutate original snapshot bytes. A later reversal schema/engine belongs to MT-2.5/MT-2.7 and the owning promotion/loyalty/trade-in point.

Milestone allocation locks the quote and uses current locking reads; the sum cannot exceed the approved quote amount. New allocation requires an unexpired, unpaid approved quote. Identical replay remains readable after payment; changed replay or additional allocation against a paid quote fails. The approved scope hash points to the immutable proposal scope/deliverables/validity record that MT-3.6 will own. It must not be a digest supplied by an untrusted client. Paid amounts/scope are never silently recalculated.

MT-2.7/MT-3.6 must validate that an `order_item_milestones` link belongs to the same `order_items.project_quote_id`, has quantity one and exact matching line/currency values. A bare FK does not prove these business relationships. All payment attempts continue under `payments.order_id`; callbacks lock the owning order/quote/milestone, verify the hosted provider reference/amount and inspect confirmed receipts before applying one transition. One milestone cannot be paid again through a second order. No new payment processor or duplicate paid-state column is introduced. These payment/linking workflows are not enabled here.

## Website capability and history boundary

`WebsiteCapabilities::snapshot` returns only `website-capabilities.v1`, mode, string version, two capability flags and a version/mode cache namespace. It has no secret, user, price, stock or private data. Missing publication is fail-closed; unknown operations fail closed. `assertCreationAllowed` requires the caller's transaction and locks the authoritative profile/revision until that transaction ends. Later mode publication must lock that same singleton before changing version/revision, so a creation cannot commit using an obsolete approved mode. Publication, first-publish absence races, impact review and independent concurrent publish/checkout/enquiry tests remain MT-3.7/MT-2.7.

Public discovery/new creation uses the declared operation-to-capability allowlist. Historical resource names are **not** accepted by that creation gate. Required history access uses a different, authenticated owner path: order status/invoices via verified order ownership; approved project-payment links via expiring scoped capability plus current approved/payable state; project/delivery access via an explicit account-project relationship. Never infer ownership from email, phone or matching contact text. Existing service requests/quotes lack that customer relationship; MT-3.6 must add and verify it before exposing its portal. Disabled marketing alone must not revoke those proven rights, and history access must never create a new inactive-capability order or enquiry.

The future GET `/api/v1/website-profile` returns this safe DTO and a versioned ETag. No such route is installed now. Personalized history/payment endpoints are private/no-store. Public resource cache keys include profile version and resource publication version. Reuse versioned master reads and targeted revalidation; never cache an authorization decision or globally fetch inactive domains. Common/digital/commerce content and per-mode hero/About/Contact/CTA variants reuse current CMS revision/page infrastructure. All mode-specific navigation, metadata, sitemap and loading behavior remains its planned CMS/API/Website gate.

LCP <= 2.5 s, INP <= 200 ms, CLS <= 0.1 and representative stable mobile Lighthouse 90+ remain continuous production-build acceptance targets for all three modes. Foundation builds here do not prove those future pages' performance or UI acceptance. API pagination/indexes/payload budgets, Server Components, appropriate SSR/SSG/ISR, split/lazy assets and affected-cache revalidation belong to consuming implementation points, with recorded justified exceptions rather than wholesale final-audit deferral.

## Permission and reset contracts

New POS operational/configuration grants are explicit; the original nine default POS permissions are unchanged. Outlet operations require `shops.enter`, assigned open outlet and the exact grant. Superadmins retain only POS/global capabilities, never Website role rights. Website content editors may preview modes but cannot publish modes; owner/manager may publish. Existing Website role grants remain unchanged. Customer-owned resources are not represented as an administrative grant.

Only a usable superadmin in a global (no outlet) context may pass `system.reset.*`. This capability check alone is insufficient: the later executor must refresh the authenticated account, verify recent reauthentication, exact reset-level grant, typed confirmation, current dry-run/retention/record-file counts, dependency integrity, automatic verified backup and a durable audit outside the cleared scope. It must refuse stale previews, outstanding unsafe stock/payment work or missing recovery evidence. Production execution remains separately authorized. There is no reset route or executor now.

`ResetRetention` explicitly classifies all 80 current tables for transactional, business and factory levels, and rejects new unclassified tables. `candidate_clear` is not deletion authorization. Mixed Website admin/customer identities require row selection; factory identity/configuration requires explicit minimum-bootstrap review. Backup, audit, provenance/replay/evidence and runtime records are conservatively preserved until a verified lifecycle plan addresses them. Runtime/cache invalidation does not authorize deleting durable idempotency, payment events, identifier sequences or recovery evidence.

`dependencyBarriers` discovers FK edges from retained/conditionally selected children to candidate-cleared parents. For example, retained stock units/IMEIs can reference an invoice/sale scheduled for transactional clearing. Such a reset must block, narrow its selection to unreferenced records, or retain the dependent historic closure under an approved retention rule. Do not null those pointers, disable FK enforcement, drop schema or falsify stock baselines. A selected scope that cannot meet preservation requirements cannot execute. The classifier intentionally never returns `executable=true` and does not examine/delete private rows or objects.

MT-3.8 must add row-level selection, dependency-closure ordering/cycle resolution, legal/operational retention decisions, verified backup/recovery, persistent reset audit and DB/private-object reconciliation. The file plan must distinguish live referenced objects, historical evidence, shared branding and orphans. Scope conflicts stop execution; “factory” does not override minimum access/recovery or production authorization. MT-7.1 must rehearse all three levels and restore with approved disposable fixtures.
