## Risk-based test and fixture control

- Small isolated changes: run focused tests, affected neighboring tests and scoped syntax/typecheck/style. Record changed files, impacted behavior and exact tests. Reuse a prior PASS only while relevant code, config, acceptance contract, test fixtures, database/environment and dependencies are materially unchanged; record its source SHA/date and reuse rationale. Run full regression only for applicable family/stage closure, release acceptance or demonstrated material cross-system risk, not per micro-fix or new commit.
- Never overlap runners, fixtures, resets, migrations or cleanup on the SAME mutable test DB. Execute sequentially, or establish separately owned schemas/ports/users/cache namespaces for true parallelism. Check DB identity, running processes, baseline rows and fixture ownership before running. Do not delete pre-existing/unowned/ambiguous records to force PASS. A clean-schema gate with unknown residue is BLOCKED until an independently owned disposable schema is provisioned. A single Playwright worker does not exclude other runner commands. Use `tools/run_isolated_test.py` or an independently verified exclusive orchestration for LOCAL test-DB suites; its lock includes setup and teardown.
- Before retrying, classify the exact terminal signature as PRODUCT_DEFECT, FIXTURE, ENVIRONMENT, ORCHESTRATION or UNKNOWN, including logical gate, command, source/environment identity, attempt and precise evidence. Require a justified material correction/isolation. Same equivalent failure twice OR three unsuccessful/incomplete attempts invokes inherited LOOP_GUARD: stop equivalent retries, diagnose and change strategy. Missing terminal evidence is not PASS; unchanged broad audits and already-PASS tests are not repeated without cause.
