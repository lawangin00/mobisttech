# MT-2.4 - Inventory and stock integrity migration

The shared backend now owns acquisition, physical units, active IMEI claims, inventory adjustments, availability, movements and the stock portion of sale/reservation transactions. The [implementation ledger](../PROJECT_IMPLEMENTATION_STATUS.md) owns live progress. This checkpoint does not implement invoice creation, financial returns/refunds, payment acceptance, checkout endpoints or POS/Website inventory interfaces. Those remain their specified later points; no source business data was accessed.

## Source reuse and deliberate adaptations

Pinned authority remains POS `c61e47394e7b3db8a49cfe443c85b63835febc9b` and Website `04e7c49518f9f11f60c83ad44f9f4e2fd2539066`. Inspection used the isolated MT-1.1 exports. The verification JSON identifies the inspected source files by commit/blob/byte hash. Source migrations, product/unit identifiers, master-data helpers, physical attributes and variant-key algorithm are reused; source controllers are adapted into shared services because their outlet-session and cross-application transport boundaries cannot provide one shared transaction.

| Source contract | Target adaptation |
|---|---|
| `StockAcquisitionController` and its input wrapper | `InventoryOperations::acquire` preserves quantity, exact cost, managed buying-source selection, business/individual party identity, normalized phone/CNIC, receipt time, unit creation, option usages and stock movement. Actor/outlet/product identity is server context. |
| `InventoryController::updateImeis` | `InventoryOperations::imeis` preserves trimmed strings up to 50 characters and product-required slot count, without inventing a 15-digit/Luhn rule that the source did not enforce. A unit version replaces timestamp conflict detection. The target global binary `active_imeis` key provides concurrency-safe uniqueness instead of relying on a preflight query. |
| Inventory corrections, damage/loss and soft delete | Positive correction creates new blank units; negative tracked adjustment retires exactly one unheld physical unit, keeps history and removes current claims. Aggregate negative adjustment excludes holds. Archive requires zero stock and no holds. |
| `ReservedInventory`, `WebsiteOrderReservationService`, `WebsiteOrderConfirmationService` | `StockLedger` and `TransactionalStock` preserve aggregate versus physical allocation, complete-slot eligibility, raw variant grouping, stock consumption and release. MySQL locks replace the former cross-repository authority split. No legacy HTTP call is copied. |
| Source product/unit/IMEI/acquisition/movement columns | Existing shared schema and source-qualified maps are retained. `StockImporter` adds acquisition, movement and IMEI row imports; MT-2.3's importer continues to own product/unit rows. Historical IMEI occurrences are separate from the one global current claim. |
| Private acquisition images | `AcquisitionDocuments` validates JPEG/PNG content and the source 5 MB limit, uses existing immutable private objects, and authorizes every attach/read against the current POS grant and outlet. No request-supplied path or public URL is accepted. |

Unit attributes still use the MT-2.3 managed-attribute service. Financial customer returns, including construction of a new returned physical occurrence rather than rewriting a sold occurrence, remain MT-2.5. Imported historic duplicates are preserved and tested; an arbitrary manual `customer_return` adjustment is intentionally not exposed as a substitute for the required return transaction.

## Application and transaction contracts

`InventoryOperations` is the authorized inventory application entry point. It refreshes the actor/outlet and requires `shop.inventory`. Its strict field allowlists reject supplied stock counters, actor/outlet IDs, file paths and state overrides. Buying-source options are locked and revalidated. New acquisition and correction units use the existing immutable product/unit codes and increasing unit numbers under the product lock. Blank tracked units count as on-hand but cannot be sold/reserved until their required IMEIs are complete.

Every inventory mutation uses a transaction with three bounded deadlock attempts. An actor/operation/idempotency key locks its durable request record before the product. Identical retries return the committed response; changed requests using the same key fail. Failed transactions leave neither a completed key nor partial acquisition, unit, claim, movement, audit or catalogue event. The key is not discarded using a short cache TTL. Server-derived audit references exclude seller documents, costs and IMEI payloads. JSON object field ordering is not a response contract.

`StockLedger` and `TransactionalStock` are internal primitives, not authorization boundaries or routes. They reject use without an owning database transaction. Future sales/order application services must authorize the caller, lock the business aggregate and create/validate its financial records in that same transaction, calling stock operations in ascending product order and retrying the entire transaction up to three times. They must not call a stock primitive after committing an invoice/payment, expose arbitrary sale/line IDs to customers, or infer payment acceptance from a stock result.

Inventory decisions use current locking reads even when an earlier query established a MySQL repeatable-read snapshot. Product locks serialize operations for the same product; units and IMEI rows are read under locks before allocation decisions. The global unique IMEI constraint arbitrates competing products. The existing generated active-unit/allocation constraint provides a second database safeguard. `ProductDefinitions` now also reads holds using a current lock so an old transaction snapshot cannot allow a definition change over a newly committed hold.

`snapshot` checks cached quantity against physical in-stock unit count, active claim/history identity, outstanding holds and negative counters. Discrepancies fail explicitly; no quantity or history is silently repaired. Quantity availability is on-hand less current allocation quantity. Physical availability consists only of in-stock, complete-slot units excluding held units, filtered by the existing raw variant key when requested. Incomplete units are reported separately. This internal snapshot includes models for transactional selection; it is not a public DTO. Later public APIs must use explicit metadata/availability allowlists, visibility checks and never expose costs, seller evidence or IMEIs.

`reserve` validates the persisted line's order/item/product/outlet/quantity relationships, requires an active unexpired or held-COD reservation, and allocates without decrementing on-hand. Repeated allocation of the same live line returns its existing allocations; closed allocation history cannot be resurrected. `consumeSale` validates the persisted sale/invoice/product/outlet and optional order line, consumes exactly its reserved units or unheld availability, increments sold quantity and records one movement per sale. It retires current claims and preserves sold unit/IMEI history. Replayed consumption cannot decrement twice. Full invoice calculation, document numbering, return/refund state and business authorization are not claimed here.

Release changes allocation/reservation state without incrementing stock. Therefore release or expiry after stock consumption cannot restore sold stock. Only overdue `active` reservations may expire; the equality boundary is expired. `held_cod` never expires automatically. The later order application owns bounded reservation creation deadlines and final confirmation state. These adapters contain no provider calls or background expiry scheduler. Multi-line orchestration must remain one owning transaction, including all products and state changes.

Acquisition image bytes are stored outside stock transactions, then the immutable object key is attached in a short authorized transaction. Attachment/read is scoped by the acquisition's outlet; acquisition metadata omits paths. A crash or failed attachment after storage can leave an unreferenced private object. Do not expose or overwrite it; a future audited retention/garbage-collection workflow must handle such objects. Attachment is a separate post-receipt operation, never evidence that the stock transaction itself succeeded.

## Offline migration and reconciliation

`StockImporter::import(runId, table, completeRow, sourceTimezone)` accepts only an explicit target `stock_rehearsal` run and POS acquisition/movement/IMEI tables. It extends the strict source decoder for enum/tiny-integer stock columns; the stock importer checks allowed states. All known columns are required, money remains exact decimal strings, explicit UTC/Asia-Karachi timestamps convert to UTC, and every parent uses its source-qualified identity map. Import product/option/outlet parents first, acquisitions before units, then IMEIs/movements; financial dependencies must wait for their mapped parent batches. Import does not replay old movements as new stock changes.

Cross-product/outlet references, invalid arithmetic, unknown movement reference types, unresolved parents, malformed IMEI history, active duplicates, changed replay and supplied private source paths quarantine atomically. Reasons and digests are retained without private row payloads. Source CNIC image paths require the separately approved private-object migration manifest; they are neither copied nor silently cleared to pass a row. Offline imports refuse held products. They are migration tools, not live APIs or permission to import real data.

`reconcile(productId)` checks the physical/current-claim/hold snapshot, movement arithmetic, continuity and final recorded balance. A recorded opening balance is retained; missing history is explicitly reported as `no_history_requires_baseline_approval`, not fabricated. Conflicting snapshots or movement chains block reconciliation. Historical duplicate sold/retired IMEIs remain distinct from an eligible later current claim. Real migration promotion still requires full source manifests, approved baseline/history coverage, all dependent financial rows, private-object reconciliation and the H-03 authorization gate.
