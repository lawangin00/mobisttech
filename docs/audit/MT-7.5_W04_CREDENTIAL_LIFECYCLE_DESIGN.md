# MT-7.5 W04 — merchant credential lifecycle implementation contract

**Status: DESIGN / IMPLEMENTATION GATES, NOT ACCEPTANCE. W04 IN PROGRESS (15/27 DONE, 12 OPEN).** This scoped contract resolves the implementation sequence for the historical Website source credential/settings gaps. It does not claim that the legacy admin setting routes, credentials, provider integrations or refunds have been migrated, and it does not authorize live payments.

## Existing verified boundary

- The current Admin payment-status page (`GET /internal/admin/website/payment-settings`) and JSON status (`GET /internal/admin/website/payment-channels`) are read-only, protected by Admin identity and `website.payments.manage`, and intentionally return only safe channel status. The Platform Administration navigation link is permission-gated. The static provider configuration lives in `backend/config/commerce.php`; it is **not** an editable or versioned merchant account.
- `PaymentProviders` is the shared provider registry. The W04 registry hardening source commit `e6c8062b2cc10416490147506656f5692648e937` constrains adapters to JazzCash/Easypaisa/card and rejects duplicate registration, preventing silent replacement of an existing verifier. The dedicated synthetic regression is commit `b6ad42ac907343e33bf8339053c5d4ab029a8f3c`; hosted CI was requested separately and must be linked after its terminal outcome is verified. Neither the adapter hardening nor its synthetic test is an authentic vendor integration.
- External channels remain default-OFF. COD is an internal collection and has no wallet/card credentials. No Website bank transfer, split tender, local PAN/CVV intake or purported live gateway credential belongs to this lifecycle.
- **Owner authority is not yet enrolled by default:** `backend/config/identity.php` leaves `offline_owner_recovery.enabled=false` and `owner_admin_public_id=''` until separately authorized enrollment. `OfflineOwnerRecovery::isBoundOwner()` requires an exact enrolled Admin public ID, a usable account, protected role and explicit permissions; a delegated Full Access role or `website.payment-credentials.manage` permission alone does not establish proprietor identity. Offline-owner recovery enrollment must not be silently repurposed as payment credential authorization. Until payment-specific owner identity is explicitly bound and accepted, production credential mutation remains a hard stop; do not create a broad role-only bypass or a synthetic owner identifier.

## Required bounded implementation order

1. **Vendor-specific contract gate (H-02):** independently obtain the authorized merchant/processor specification for each gateway. Record the exact environment, merchant identifier format, credential key allowlist, authenticated request/callback/webhook algorithm, redirect-domain requirements, supported payment/refund/status operations, settlement correlation and expiry/rotation policy. Do not fabricate a common wallet signature, unknown processor fields or a live merchant identity. A gateway without an approved contract has no writable credential schema and remains unavailable.
2. **Separate encrypted credential store:** design a dedicated per-provider/per-environment credential record with ciphertext-only secret fields, immutable safe event history, per-provider key versions, creator/rotator IDs, and concurrency-safe version checks. Use Laravel encryption/KMS-backed secret material as approved; never put plaintext secrets in `site_configuration_revisions`, public configuration, Inertia props, logs, audits, exception text, browser storage or Git. Retain or purge superseded ciphertext only under an explicit security/retention policy. A successful write must not implicitly set `commerce.providers.*.enabled` or register an adapter.
3. **Owner-only mutation:** require authenticated Admin realm, the dedicated `website.payment-credentials.manage` permission, an explicitly enrolled payment-owner identity (not simply a delegated display permission or independently enrolled offline-recovery owner), recent reauthentication, CSRF validation, strict per-vendor request-field allowlisting, input size limits and throttling. Keep separate masked status read vs write grants; do not return any secret even immediately after successful submission. Audit only provider, environment, safe operation, credential version and actor, never secret values or raw request body. Deny stale versions and concurrent double rotations without partial writes.
4. **Nonsecret settings workflow:** separately version permitted channel labels/instructions/COD limits and proposed merchant metadata as draft/preview/publish/rollback operations with explicit permissions and audit. Secrets are never included in a settings revision or copied by rollback. Distinguish `configured`, `approved`, `enabled`, `adapter_verified` and `available`; publishing nonsecret settings must never bypass H-02 or the runtime fail-closed checks. Do not silently convert a staged `merchant_configured` flag into actual verified readiness.
5. **Controlled activation and evidence:** activation must be an explicit, separately authorized operation only after vendor-authentic sandbox fixtures, redirect/webhook signature and anti-replay checks, owner/order/amount/currency checks, refund/error/reconciliation cases, and settlement evidence have been accepted. Hosted card payment data stays with the selected processor; the target must not accept raw card numbers or CVV. Keep a documented emergency disable and key-rotation/rollback procedure that cannot restore a compromised previous secret.

## Mandatory acceptance matrix before W04 may close

- `GET` masked status: guest 401; unrelated Admin 403; payment-settings reader sees only permitted nonsecret status; secret-only permission must not grant broad payment-admin visibility. Cross-provider and cross-environment secret access fails closed.
- Write and rotation: non-owner/delegated-only, unbound payment-owner identity, stale session, wrong CSRF, unsupported provider, unapproved merchant contract, unknown/extra/missing fields, raw-card fields, stale version and duplicate submission all reject without credential/configuration/audit side effects. Authorized rotation updates only its provider+environment and increments one version atomically; previous credentials never appear in HTTP/HTML/error/log responses.
- Activation: encrypted storage or even an approved configuration draft does not alone make `checkoutChannels().available` true. A registered, authentic, contract-approved adapter plus explicit authorized activation is independently required; forced `enabled=true` without a registered adapter or required merchant configuration must remain unavailable.
- Genuine vendor signed callbacks/webhooks, hosted redirects, provider failure/retry/replay/refund, settlement reconciliation, and authorized sandbox records are **EXTERNAL UNVERIFIED / H-02 HOLD** until real contractual evidence is supplied. Synthetic tests are limited target security coverage, not permission to go live.

**Next implementation:** reconcile the explicitly bound payment-owner authority and approved provider field contracts before exposing protected credential writes; then build the isolated encrypted store and masked lifecycle. The current run changes only the registry/negative test; no credentials, production adapter, payment settings mutation, or provider activation was introduced.
