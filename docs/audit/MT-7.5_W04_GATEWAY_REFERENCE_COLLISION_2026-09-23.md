# MT-7.5 / W04 — Provider reference collision guard (23-Sep-2026)

- Root cause: payment initiation previously persisted a provider-returned `gateway_order_reference` without checking whether another payment in the same gateway already owned it. The receipt matcher selects by gateway and `(gateway_order_reference OR local public_id)` before verifying merchant/mode; a reused reference could therefore resolve to the wrong order, particularly after merchant/environment rotation.
- Test-first synthetic regression demonstrated two pending Website payments accepting the same vendor reference. The new transactional initiation guard rejects conflicting gateway references, including across merchant/mode rotation, before binding the second payment; it also rejects a provider reference shadowing a different local payment public ID for that gateway.
- New migration `2026_09_23_054000_unique_gateway_payment_reference.php` enforces the non-NULL `(gateway, gateway_order_reference)` uniqueness at MySQL level across independently running workers; multiple NULL, not-yet-initiated references remain allowed. Migration ran on the isolated testing database. Direct duplicate database update is rejected in the regression.
- This is a target-side fail-closed invariant, not evidence of a genuine provider-specific reference format or external integration. Provider callback disable, merchant credential lifecycle, refunds and settlement remain H-02 HOLD. W04 IN PROGRESS; MT-7.5 15/27 DONE, 12 OPEN.
